# Bon Atlas — сайт на Astro + Sveltia CMS

## Автоматическая загрузка новых медиа

Новый файл сначала положите в `public/uploads/` (или `public/images/`), затем зарегистрируйте только его:

```powershell
python scripts/media.py register --file uploads/blog/kak-postroit-scenu-cover.png
```

Путь `--file` задаётся относительно `public/`; параметр можно повторить.
Команда копирует точные байты в `media/objects/<sha256>/<имя>` и обновляет
`media-manifest.json`. В коммит добавляются manifest, созданные объекты и
ссылки на медиа в контенте. Исходники в `public/images` и `public/uploads`
по-прежнему исключены из Git. Файлы `media/objects` хранятся без перевода
окончаний строк. Максимальный размер нового объекта в Git — 50 MiB.

После push в `develop` или `main` общий этап `media` проверяет manifest и
хеши новых объектов, затем последовательно синхронизирует DEV и PROD.
FTP-пароль берётся из существующего GitHub Secret `REG_FTP_PASSWORD`.
Страницы публикуются только после успешной синхронизации; добавление медиа
на прод само по себе не выпускает DEV-контент. Редактор `/atlas/app/` не затрагивается.

Адрес каждого файла содержит SHA-256. Существующий объект того же размера
считается ранее проверенным и повторно не передаётся. Новые загрузки
проверяются чтением и сравнением SHA-256. Коллизия размера/занятый адрес
останавливает загрузку вместо перезаписи. Изменение изображения создаёт
новый адрес; старые объекты сохраняются для прежних страниц и откатов.
Параллельные синхронизации сериализованы общей группой concurrency.

Старые файлы можно оставить на хостинге: их не требуется добавлять в Git.
Если старое медиа отсутствует на сервере, нужны его исходные байты; CI
сообщит об этом, а не опубликует страницу с отсутствующим изображением.
Ручной запасной путь: `python scripts/media.py upload --environment both`.
Регистрация без `--file` сохраняет прежний режим сканирования локальной
библиотеки и не добавляет все старые изображения в Git.

В этой папке находятся исходные материалы передачи и рабочий скелет сайта. Основной URL реализации — `https://bonatlas.ru`; блог и статическая админка Sveltia CMS включены в технический каркас.

## Быстрый старт

Требуется Node.js `22.22.0` или новее.

```bash
npm install
npm run dev
```

Проверки production-сборки:

```bash
npm run check
npm run build
```

Основные маршруты: `/`, `/atlas`, `/plot`, `/blog`, `/admin/`.

### Локальная работа с CMS

1. Запустите `npm run dev`.
2. Откройте `http://127.0.0.1:4321/admin/index.html` в Chrome или Edge.
3. Нажмите «Работать с локальным репозиторием» — вход в аккаунт не требуется.
4. Выберите корневую папку `bonatlas-site-handoff`.

Кнопка обычного GitHub OAuth скрыта, пока не настроен отдельный OAuth-клиент. Для удалённой работы сначала замените `local/bonatlas-site` в `public/admin/config.yml` на настоящий `owner/repository`; затем можно войти через GitHub token или подключить Sveltia CMS Authenticator.

Для Vercel добавлен `vercel.json`; достаточно импортировать репозиторий, команда сборки и папка результата будут определены автоматически.

## Исходные материалы передачи

Ниже сохранено описание исходного пакета. Основной домен в нём и в текущей реализации совпадает — `bonatlas.ru`. Отличие технического каркаса: подключены Sveltia CMS и демонстрационные статьи блога.

Исходный пакет содержит основу первой версии сайта для двух продуктов: Bon Atlas и Bon Plot.

## Порядок работы

1. Передай агенту нового проекта `CONTENT_SPEC.md` как источник истины по текстам и продуктовым фактам.
2. Передай `SITE_BUILD_PROMPT.md` как основную задачу на проектирование и сборку сайта.
3. Передай `CONTENT_GAPS.md` как реестр неизвестных значений и решений перед публикацией.
4. Передай `SITE_REFERENCES.md` как приоритизированную подборку визуальных и структурных ориентиров.
5. Попроси агента сначала вернуть карту маршрутов, компоненты и список блокирующих данных, а не писать весь сайт без согласования.

## Состав пакета

- `CONTENT_SPEC.md` — позиционирование, структура, готовые тексты страниц, SEO-метаданные, FAQ, правила визуальных материалов и ограничения обещаний.
- `SITE_BUILD_PROMPT.md` — исполнимое техническое задание для отдельного Astro-проекта с Cosmo, техническим SEO и критериями приёмки.
- `CONTENT_GAPS.md` — домен, контакты, формы, юридические данные, загрузки, системные требования, приватность и материалы, которые ещё нужно подтвердить.
- `SITE_REFERENCES.md` — сайты-референсы для картографического и писательского продуктов, антипаттерны и рекомендуемая комбинация визуальных приёмов.

## Зафиксированные решения

- Основной домен первой версии — `bonatlas.ru`.
- Bon Atlas остаётся общим брендом для экосистемы инструментов.
- У сайта один домен и две продуктовые страницы: `/atlas` и `/plot`.
- Слоган главной: «Создавайте миры. Рассказывайте их истории.»
- Настольные приложения и их локальная работа — текущий продуктовый фокус.
- Веб-редакторы, поддомены приложений, оплата и личный кабинет не входят в первую версию.
- Блог получает техническую основу, но статьи пока не создаются и пустой раздел не выводится в меню.
- Настоящие скриншоты будут добавлены позже; до этого используются честно подписанные плейсхолдеры.

## Граница ответственности

Этот пакет не является репозиторием сайта и не меняет приложение Bon Atlas. Новый сайт создаётся отдельным проектом. Неизвестные значения нельзя заменять догадками: до их заполнения соответствующие элементы скрываются, переводятся в честный статус подготовки или закрываются от индексации.

## Браузерный Bon Atlas: подготовка выпуска

Актуальное уточнение к исходному пакету: существующая страница `/atlas/` описывает браузерный редактор. Сам редактор разрабатывается и публикуется другим проектом в `/atlas/app/`. Его исходники и сборку в Astro не добавлять. CTA на странице ведут на `/atlas/app/`.

Сайт пока размещён на «Хост-Лайт». Обратная связь в редакторе временно работает через Google Forms; ссылку и интерфейс формы ведёт проект редактора. PHP-endpoint `/atlas/api/feedback.php` не включён. Его черновик сохранён вне `public/`, в `drafts/atlas-feedback/feedback.php`. Подготовка релиза исключает случайно оставшуюся копию endpoint, а загрузка релиза отклоняет этот путь.

`scripts/site_paths.py` задаёт границу владения: сайт не загружает, не резервирует, не перезаписывает и не удаляет `/atlas/app/`. Защита применяется при обычном выпуске, обходе сайта без `release.json`, восстановлении после ошибки и ручном откате старых резервных копий. Если редактор случайно окажется в сборке сайта, подготовка релиза завершится ошибкой. Старые манифесты и снимки с файлами редактора фильтруются при чтении; сам редактор остаётся на сервере.

Перед публикацией страницы получить подтверждение проекта редактора и проверить на продакшене: `/atlas/app/` открывает редактор; создание карты, сохранение/повторное открытие проекта, экспорт PNG и сохранение/импорт JSON работают; ссылка на Google Forms открывается. Не считать ответ HTTP 200 подтверждением этих функций. До этой проверки страницу со статусом доступности не публиковать и не запускать автодеплой push-командой. Порядок запуска GitHub Actions остаётся прежним.
